# Wakefinder

Отдельный MEV searcher-бот (слежка за мемпулом → симуляция AMM → отправка бандла
через Flashbots/Jito) на Ethereum и Solana. Независим от BitbotBY — этот проект
on-chain, BitbotBY — CEX/ccxt.

Две независимые стратегии на каждой из двух сетей — 4 отдельных процесса:

| | Ethereum | Solana |
|---|---|---|
| **Арбитраж** | `wakefinder/chains/eth/main.py` | `wakefinder/chains/solana/main.py` |
| **Копитрейдинг** | `wakefinder/chains/eth/copytrade.py` | `wakefinder/chains/solana/copytrade.py` |

Что делать при срабатывании kill switch/drawdown/других защит — см. [RUNBOOK.md](RUNBOOK.md).

## Архитектура

```
                    ┌─────────────────────────────────────────┐
                    │        конфиг-профиль (TOML)             │
                    │  chain + strategy + пулы/кошельки/риск   │
                    └──────────────────┬────────────────────────┘
                                       │  wakefinder run <profile.toml>
                                       ▼
                    ┌─────────────────────────────────────────┐
                    │            wakefinder/cli.py              │
                    └──────────────────┬────────────────────────┘
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
     chains/eth/main.py      chains/eth/copytrade.py   chains/solana/{main,copytrade}.py
     (арбитраж)               (копитрейдинг)            (то же на Solana)
              │                        │                        │
              └────────────┬───────────┴────────────┬───────────┘
                           ▼                        ▼
                  ┌──────────────────────────────────────┐
                  │      wakefinder/common/ (общее)        │
                  │  killswitch · drawdown · consensus     │
                  │  adaptive_tip · allowlist · trade_log  │
                  │  wallet_stats · alerts · heartbeat     │
                  │  reconnect · keystore · price_feed     │
                  └──────────────────────────────────────┘
```

Каждый из 4 процессов — независимый watcher→simulator→sender конвейер
(`common/interfaces.py`: `MempoolWatcher`/`Simulator`/`BundleSender`, не
привязаны к конкретной сети). Общая инфраструктура (риск-контроль,
логирование, алерты) шарится через `common/`, но **у каждого процесса
должен быть свой кошелёк** — параллельная отправка транзакций с одного
кошелька из разных процессов ломает подсчёт nonce.

**Через что торгуем** (архитектурное решение, не настройка): на Ethereum —
Uniswap V2 и совместимые форки (Sushiswap) через прямой вызов роутера; на
Solana — [Jupiter](https://jup.ag) агрегатор, а не собственная кодировка
инструкций конкретного DEX (Raydium/Orca — слишком много PDA-выводов, чтобы
доверять без devnet-проверки). Это зашито в `chains/eth/abi.py`/`sender.py` и
`chains/solana/*.py` — не параметр конфига.

**Многосетевой охват**: добавить ещё одну EVM-сеть (BSC/Arbitrum/Base/...) —
дёшево: копируете `chains/eth/` почти 1:1, меняются адреса роутера/фабрики/WETH
и RPC URL — большинство таких сетей используют форки того же Uniswap V2 ABI.
Не-EVM сеть, отличная от Solana — полноценный новый chain-модуль с нуля, как
Solana в своё время. Ни то, ни другое не реализовано сейчас — только архитектурно готово.

## Быстрый старт: от нуля до первого запуска

### 1. Установка

```bash
git clone <этот репозиторий>
cd Wakefinder
pip install -e ".[dev]"
```

### 2. Заведите отдельный кошелёк

**Никогда не используйте основной кошелёк.** Заведите новый, ТОЛЬКО для бота:
- Ethereum: любой стандартный способ (MetaMask → "Create Account", `eth_account.Account.create()` в Python, `cast wallet new` из Foundry) — нужен приватный ключ в hex (`0x...`).
- Solana: `solana-keygen new` (Solana CLI) или Phantom/Solflare → "Create New Wallet" → экспорт приватного ключа (base58).
- Держите на нём **минимальный баланс**, регулярно выводите прибыль на холодный кошелёк.
- Для Ethereum-арбитража нужен ЕЩЁ ОДИН отдельный ключ — `FLASHBOTS_SIGNER_KEY`, только для репутации у relay, никогда не финансируется.
- Секрет храните либо plaintext в `.env` (проще, начните с этого), либо через шифрованное хранилище — см. раздел "Безопасность" ниже.

### 3. Получите доступ к RPC

- **Ethereum**: нужны ОБА — WS-эндпоинт (подписка на мемпул) и HTTP-эндпоинт, который поддерживает `eth_getRawTransactionByHash` (не все провайдеры это дают — проверьте в документации провайдера, бот падает громко, если его нет). Варианты: [Alchemy](https://alchemy.com), [Infura](https://infura.io), [QuickNode](https://quicknode.com) — у всех есть бесплатный тир, для реальной торговли из-за скорости/лимитов обычно берут платный.
- **Solana**: тоже WS + HTTP. Варианты: [Helius](https://helius.dev), [QuickNode](https://quicknode.com), [Triton](https://triton.one). Публичный `api.mainnet-beta.solana.com` для продакшена не годится (жёсткие rate-лимиты).
- **Тестнет обязателен перед реальными деньгами**: Ethereum Sepolia (RPC — те же провайдеры, отдельный эндпоинт; ETH — из faucet, например `sepoliafaucet.com`), Solana devnet (`solana airdrop` через CLI или `solfaucet.com`).

### 4. Найдите, за чем следить

- **Пулы для арбитража**: нужен адрес целевого пула И адрес референсного пула ТОЙ ЖЕ пары на ДРУГОМ DEX (без второго источника ликвидности арбитража нет). Ethereum — [Etherscan](https://etherscan.io) (вкладка контракта пары) или [Dexscreener](https://dexscreener.com); Solana — [Solscan](https://solscan.io), [Dexscreener](https://dexscreener.com), сайты Raydium/Orca.
- **Кошельки для копитрейдинга**: сам блокчейн не размечает адреса по "умности" — источники:
  - Ручная/внешняя аналитика: [Nansen](https://nansen.ai), [Arkham](https://arkham.com), [DeBank](https://debank.com), Etherscan "Top Accounts".
  - Наш `wakefinder/wallet_scanner.py` — первый дешёвый фильтр: `find_candidate_wallets_eth`/`find_candidate_wallets_solana` находят, кто вообще торговал в интересующих пулах и как часто (тот же RPC, без нового источника данных), опционально `filter_by_etherscan_activity` отсекает свежие/одноразовые адреса. Это список кандидатов, не готовый вердикт — финальную курацию всё равно делаете вы или внешняя аналитика.

### 5. Настройте секреты и профиль

```bash
cp .env.example .env   # впишите RPC/ключи — .env никогда не коммитить
```

Затем скопируйте и отредактируйте подходящий профиль из `configs/` (адреса
внутри — заглушки, замените на найденные на шаге 4):

```bash
cp configs/eth-copytrade-conservative.toml configs/my-profile.toml
# отредактируйте watched_wallets, token_denylist, риск-параметры
```

Про формат профилей и как переключаться между стратегиями/скоростными режимами — раздел "Конфиг-профили и CLI" ниже.

### 6. Проверьте на тестнете

Смените `.env` на тестнетовые RPC/ключи (Sepolia/devnet), запустите с
минимальным капиталом, убедитесь, что весь цикл (обнаружение → симуляция →
отправка → лог) реально работает, прежде чем касаться mainnet-капитала. Это
единственный шаг, который бот не может проверить сам за вас.

### 7. Запустите

```bash
wakefinder run configs/my-profile.toml
```

(или `python -m wakefinder.cli run configs/my-profile.toml`, если без `pip install -e .`)

### 8. Мониторьте

```bash
python -m wakefinder.dashboard              # открытые позиции + статистика по кошелькам
python -m wakefinder.common.killswitch status
```

Настройте `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` в `.env` для алертов. При
срабатывании kill switch/просадки/других защит — [RUNBOOK.md](RUNBOOK.md).

## Конфиг-профили и CLI

`wakefinder/cli.py` — единая точка входа поверх TOML-профилей вместо
захардкоженных launcher-скриптов на каждую комбинацию сеть+стратегия.

```bash
wakefinder run configs/eth-arb.toml
wakefinder run configs/eth-copytrade-fast-memecoin.toml
```

Профиль (см. примеры в `configs/`) задаёт:
- `chain` (`"eth"`/`"solana"`) и `strategy` (`"arb"`/`"copytrade"`/`"snipe"`) — какой `run()` вызвать;
- `[[pools]]`/`[[reference_pools]]`/`[[solana_pools]]` — пулы (формат под каждую сеть, см. примеры);
- `watched_wallets`, `token_allowlist`, `token_denylist` — списки адресов;
- `[risk]` — переопределение риск-параметров `Settings` (полный список ключей — `_RISK_ENV_MAP` в `cli.py`), применяется через переменные окружения ДО первого чтения конфига в процессе;
- `kill_switch_file` (опционально) — см. "Выборочное выключение" ниже.
- `live_config_file` (опционально) — свой файл живого конфига на этот
  профиль, см. "Живой конфиг"; без него — общий файл на все процессы.

**Один процесс = один профиль** — то же допущение, что и раньше про раздельные кошельки/процессы на стратегию.

### Поиск кандидатов в watched_wallets

`wakefinder discover` — CLI поверх `wallet_scanner.py`, а не разрозненные
функции, которые нужно было вызывать из Python вручную:

```bash
wakefinder discover --chain eth --pools 0xПУЛ1 0xПУЛ2 --from-block 21000000 --to-block 21010000 --top 20
wakefinder discover --chain solana --pools 0xVAULT1 --limit 1000
```

Печатает ранжированных по частоте торговли кандидатов и готовый
TOML-фрагмент для `watched_wallets` — copy-paste в профиль, не автозапись
(в TOML нет стандартного writer'а в stdlib, а тихая перезапись чужого файла
конфига — плохая идея сама по себе). `--etherscan-api-key` — тот же
опциональный фильтр по активности, что и в `filter_by_etherscan_activity`.

### Выборочное выключение: несколько профилей одновременно

Общий kill switch (см. "Портфельный риск-контроль") останавливает СРАЗУ все
4 процесса — это осознанно для аварийной ситуации, но неудобно, если нужно
выключить только сегодняшнюю стратегию, оставив остальные работать. Профиль
может задать свой независимый kill switch:

```toml
kill_switch_file = "~/.wakefinder_kill_eth_fast_memecoin"
```

Если не задано — процесс использует общий (поведение как раньше). С
отдельным путём можно управлять именно этим профилем:

```bash
python -m wakefinder.common.killswitch stop --path ~/.wakefinder_kill_eth_fast_memecoin
```

Не отменяет общий kill switch — он всё ещё останавливает всё сразу,
независимо от того, задан ли у процесса свой отдельный путь.

### Мемкоин-профиль: конкурируем с китами, не опаздываем

`configs/eth-copytrade-fast-memecoin.toml` — **не новая стратегия и не новый
код**, тот же `chains/eth/copytrade.py`, что и в консервативном профиле,
только другие числа риска. Единственный по-настоящему крупный рычаг скорости,
целиком в наших руках — окно консенсуса:

| Параметр | Консервативный | Быстрый (мемкоин) | Почему |
|---|---|---|---|
| `copytrade_min_consensus_wallets` | 3 | 1 | ждать второго кита = отдать движение цены тем, кто не ждал |
| `copytrade_consensus_window_seconds` | 180 | 5 | при `wallets=1` не влияет, но безопасный дефолт |
| `copytrade_size_pct` | 2% | 0.5% | меньше на сделку — плата за повышенный риск скорости |
| `copytrade_stop_loss_check_interval_seconds` | 60 | 5 | мемкоины волатильнее — раз в минуту слишком редко |
| `min_reference_liquidity_eth` | 1.0 | 0.1 | у свежих мемкоинов пулы обычно мельче дефолтного порога |

Остальные стадии пайплайна (обнаружение pending-tx, отправка в публичный
мемпул) уже настолько быстрые, насколько это возможно без колокации/приватного
ордерфлоу — это осознанно вне охвата проекта (см. "Безопасность").

**Чек-лист перед реальным запуском мемкоин-профиля** (операционная
ответственность, не технический баг):
- [ ] `token_denylist` вручную укомплектован известными fee-on-transfer/rebasing токенами, которые собираетесь торговать через whitelisted пары — у мемкоинов это встречается намного чаще, чем у голубых фишек.
- [ ] Понимаете, что снижение `MIN_REFERENCE_LIQUIDITY_ETH`/`_SOL` — это прямое снижение защиты от манипуляции ценой (раздел "Инфраструктурная надёжность"), не бесплатная опция.
- [ ] `copytrade_max_total_exposure_pct` выставлен с учётом того, что позиции в мемкоинах могут обнулиться (rug pull) — стоп-лосс не защищает от полной потери ликвидности пула.
- [ ] Арбитраж-профиль на мемкоины НЕ настраивается — у свежего токена обычно нет второго ликвидного пула на другом DEX, а без него арбитража по конструкции нет.

## Портфельный риск-контроль (все 4 процесса: ETH/Solana × арбитраж/копитрейдинг)

- **Единый kill switch** (`wakefinder/common/killswitch.py`) — все 4 процесса
  проверяют ОДИН файл (по умолчанию абсолютный путь в домашней директории,
  не зависит от рабочей директории процесса). Управление:
  ```bash
  python -m wakefinder.common.killswitch stop     # остановить всё
  python -m wakefinder.common.killswitch resume    # снять
  python -m wakefinder.common.killswitch status
  ```
- **Circuit breaker по просадке** (`wakefinder/common/drawdown.py`) —
  независимо от `MAX_CONSECUTIVE_FAILURES` (тот ловит только "бандл не
  попадает в блок"), считает суммарную РЕАЛИЗОВАННУЮ прибыль/убыток по всем
  стратегиям одной сети за скользящее окно (`DRAWDOWN_WINDOW_SECONDS`, по
  умолчанию 24ч), плюс НЕРЕАЛИЗОВАННУЮ переоценку всех открытых
  копитрейд-позиций на момент проверки (копитрейд-энтрипоинты сами
  переоценивают позиции живым RPC/quote-запросом и передают число в
  `check_drawdown(unrealized_pnl=...)`) — и сам включает kill switch при
  превышении `MAX_DRAWDOWN_ETH` / `MAX_DRAWDOWN_SOL`.
- Оба реализуют Tier 0 из архитектурного аудита; третий пункт Tier 0 —
  реальная валидация на testnet/devnet — не может быть сделана автоматически,
  нужны профинансированные тестовые кошельки и живой RPC-провайдер (см.
  "Быстрый старт" шаг 6).

### Поэтапный ввод капитала (canary)

`wakefinder/common/canary.py` — зеркало circuit breaker'а по просадке:
та останавливает при убытке, эта постепенно РАЗГОНЯЕТ размер позиции, пока
убытка нет. По умолчанию выключен (`CANARY_START_FRACTION=1.0` — сразу
полный размер, поведение не меняется, пока не включите явно в профиле).

Включённый (`CANARY_START_FRACTION < 1.0`): `max_capital_per_bundle_eth/sol`
и `copytrade_size_pct` стартуют от заданной доли и линейно растут до 100% по
мере накопления `CANARY_RAMP_TRADES` подтверждённых (`included`) сделок —
не по времени, а по реальному количеству живых попыток. Работает поверх уже
запущенного процесса: `CanaryController` держит оригинальные значения из
конфига и на каждой проверке (тот же таймер, что у drawdown) масштабирует
их заново от оригинала, не от уже уменьшенного текущего значения.

Пригодится при первом запуске нового `watched_wallets`-набора или новой
пары, которым ещё не хотите доверять полный размер с первой же сделки.

## Инфраструктурная надёжность (Tier 1–2)

- **Защита референсного пула от манипуляции** (`MIN_REFERENCE_LIQUIDITY_ETH` /
  `_SOL`, по умолчанию 1 ETH / 10 SOL) — тонкий референсный пул дёшево
  сдвинуть в том же блоке/слоте, что и атакуемый, подсунув боту фиктивно
  прибыльную котировку; симулятор на обеих сетях отказывается доверять
  пулам ниже порога.
- **Автопереподключение WS** (`wakefinder/common/reconnect.py`) — все 4
  watcher'а обёрнуты в `with_reconnect`, который перехватывает обрыв
  соединения (провайдер рестартует ноду, сетевой блип) и переподключается с
  экспоненциальным backoff вместо падения всего процесса.
- **Heartbeat** (`wakefinder/common/heartbeat.py`) — каждый процесс пишет
  timestamp в свой файл в `HEARTBEAT_DIR` каждые `HEARTBEAT_INTERVAL_SECONDS`
  (по умолчанию 30с). Ловит тихое зависание event loop, которое не даёт
  исключения (поэтому его не ловят ни kill switch, ни `with_reconnect`).
  Проверка снаружи:
  ```bash
  python -m wakefinder.common.heartbeat eth_arb.heartbeat 90
  ```
- **Process supervision** (`deploy/systemd/*.service`) — шаблоны systemd-юнитов
  с `Restart=always` на все 4 процесса. Намеренно не реализовано на Python —
  супервизия процесса это работа ОС/init-системы, а не самого бота; см.
  комментарии внутри юнитов про замену `ExecStart` на `wakefinder run <профиль>`
  (голый `python -m wakefinder.chains.*` запускается с пустыми
  `pool_registry`/`watched_wallets` — это smoke-test заглушка).

## Бэктестинг (Tier 4)

**ETH** — `wakefinder/backtest.py`: `run_backtest(w3, target_router,
reference_pools, from_block, to_block)`. Не новый источник данных: тот же
`ETH_RPC_HTTP_URL`, что и live-режим — сканирует исторические `Swap`-логи
целевых пулов через `eth_getLogs`, реконструирует `PendingSwap` по каждому и
прогоняет через ЖИВОЙ `TwoPoolArbSimulator.simulate()` (тот же код, что
реально торгует, не копия логики) на резервах ДО этого исторического свопа.

Честные ограничения:
- Публичные RPC ограничивают диапазон/глубину `eth_getLogs` — `chunk_size`
  разбивает диапазон, но для старой истории может понадобиться архивный узел.
- НЕ учитывает конкуренцию с другими searcher-ботами за тот же блок —
  верхняя граница достижимой прибыли, не гарантированный исторический результат.
- Использует ТЕКУЩИЕ `MAX_GAS_GWEI`/`MIN_REFERENCE_LIQUIDITY_ETH`/т.п., не
  исторические условия сети на момент каждого блока.

**Solana** — `wakefinder/chains/solana/backtest.py`: `run_backtest(client,
reference_pools, limit_per_pool)`. Технически иначе, чем ETH-версия — у
Solana нет `eth_call(block_identifier=...)`-эквивалента для произвольного
исторического состояния аккаунта, и нет верифицированного парсера сырых
Raydium/Orca swap-инструкций (та же причина, по которой снайпинг на Solana
использует Jupiter-подтверждение вместо разбора конкретного DEX — см.
"Снайпинг на Solana"). Вместо этого — тот же принцип, что уже в LIVE-коде
(`RaydiumVaultWatcher`): не парсим инструкцию, а читаем итоговый баланс
vault-аккаунта, который транзакция уже подтвердила
(`meta.preTokenBalances`/`postTokenBalances`) — "своп" здесь = транзакция,
где баланс ровно одной стороны vault'а вырос, а другой упал.

Честные ограничения (свои, не совпадающие с ETH-версией):
- Глубина истории — то, что хранит конкретный RPC-провайдер (тот же класс
  ограничения, что chunk_size/`eth_getLogs`-глубина у ETH).
- Резервы РЕФЕРЕНСНОГО пула на момент каждого свопа цели реконструируются
  как "последняя транзакция этого пула не позже данного слота" — если
  референсный пул торговался редко, момент может быть заметно раньше.
- Аккаунты, подгруженные через Address Lookup Table, не резолвятся —
  такие транзакции пропускаются (см. docstring модуля, апгрейд-путь описан).

## Операционные требования (путь Ethereum)

- **RPC-провайдер обязан поддерживать `eth_getRawTransactionByHash`.** Не
  универсально — если ваш не поддерживает, бот падает громко (логирует и
  пропускает возможность). Проверьте это заранее.
- **Дайте approve каждому роутеру, через который может пройти сделка** —
  целевому роутеру (`ETH_ROUTER_ADDRESS`) *и* каждому референсному роутеру,
  переданному в `reference_pools` — от кошелька `ETH_PRIVATE_KEY`, на каждый
  задействованный токен. Разовая настройка, не часть горячего пути.
- `reference_pools` должен сопоставлять каждый отслеживаемый пул с пулом той
  же пары на действительно другом DEX — бэкран против одного-единственного
  пула не является арбитражем.
- **Авто-обнаружение доп. референсных пулов** (`ETH_AUTO_DISCOVER_REFERENCE_POOLS=true`,
  по умолчанию выключено): помимо явно заданного в `reference_pools` пула,
  симулятор дополнительно спрашивает `getPair()` у других известных DEX
  (`KNOWN_DEX_FACTORIES` в `chains/eth/simulator.py` — сейчас Uniswap V2 +
  Sushiswap) на ту же пару токенов и берёт максимум прибыли среди явно
  заданного и всех найденных пулов, не ограничиваясь одним заранее угаданным
  DEX. Стоит один лишний RPC-вызов на своп-кандидат, поэтому опционально.
- Своп попадает в обработку по ИЛИ: размер (`min_amount_in`) ИЛИ отправитель
  в `watched_wallets`. Список кошельков берётся извне — см. "Быстрый старт" шаг 4.

## Безопасность

- Начинайте с тестнета (Sepolia) — никакого реального капитала, пока полный
  цикл там не проверен (см. "Быстрый старт" шаг 6).
- `MAX_GAS_GWEI` / `MAX_CAPITAL_PER_BUNDLE_ETH` в `.env` ограничивают риск на
  бандл; `ETH_ROUTER_ADDRESS` сверяется с allowlist в `config.py` —
  неизвестный роутер (опечатка или подменённый `.env`) не даёт боту запуститься.
- Бот отказывается стартовать, если `ETH_PRIVATE_KEY` и `FLASHBOTS_SIGNER_KEY`
  указывают на один и тот же кошелёк — на ключе подписи никогда не должно быть средств.
- **Шифрованное хранилище ключей** (`wakefinder/common/keystore.py`) —
  альтернатива голому ключу в `.env`. Зашифровать:
  `python -m wakefinder.common.keystore <путь>` (пассфраза и ключ вводятся
  интерактивно через `getpass`, не попадают в аргументы/историю shell). Затем
  вместо `ETH_PRIVATE_KEY` укажите `ETH_PRIVATE_KEY_FILE=<путь>` и
  `WALLET_KEY_PASSPHRASE` в окружении процесса (аналогично для
  `FLASHBOTS_SIGNER_KEY_FILE`/`SOLANA_PRIVATE_KEY_FILE`) — ровно один
  источник на ключ, plaintext ИЛИ файл, бот откажется стартовать, если задано
  и то, и другое, или ни то, ни другое. Не заменяет HSM/KMS (см. docstring
  модуля) — пассфраза всё равно должна быть в окружении живого процесса.
- Стратегия по умолчанию — backrun/арбитраж, не sandwich (sandwich напрямую
  вредит отслеживаемому трейдеру — это осознанный опт-ин, не поведение по умолчанию).
- **Kill switch**: единый на все 4 процесса, см. раздел "Портфельный риск-контроль" выше — `python -m wakefinder.common.killswitch stop|resume|status`.
- **Все секреты — `SecretStr`**: RPC URL, приватные ключи, пассфраза keystore,
  Telegram-токен — pydantic скрывает значение в `repr()`/`str()`, чтобы
  необработанный traceback/лог не слил его в открытом виде. Регрессия
  проверяется тестом (`tests/test_security.py`).
- **Предупреждение о правах доступа**: при старте `get_settings()` проверяет
  режим `.env` и всех заданных `*_KEY_FILE` — если файл читаем/писуем группой
  или всеми (не `600`), в лог идёт заметное предупреждение (не блокирует
  старт — например, в контейнере под конкретным пользователем это не всегда
  применимо). Частая причина утечки на общих серверах.
- **Сканирование зависимостей** (`pip-audit` в `.github/workflows/ci.yml`) —
  на каждый push/PR проверяет известные CVE в разрешённом дереве зависимостей.
- Баланс проверяется перед каждым бандлом — и нативный ETH (покрывает газ на
  обе ноги по комиссии, которую бот собирается предложить), и `token_in` — бот
  пропускает возможность, а не подписывает транзакцию, на которую не хватает средств.
- Tip за включение бандла масштабируется от `PROFIT_SHARE_BPS` (по умолчанию
  90%) захваченной прибыли самой возможности, а не фиксированная ставка —
  предложение цены близко к реальной выгоде возможности — именно это нужно,
  чтобы выиграть аукцион block builder'а за включение против других searcher-ботов.
- **Колокация/приватный ордерфлоу — осознанно вне охвата.** Мы не пытаемся
  конкурировать с профессиональными MEV-шопами на физической задержке
  (colocated-серверы у валидаторов, приватные сделки с билдерами) — вся
  скорость, которую можно выжать, выжимается на уровне конфига/архитектуры
  (см. "Мемкоин-профиль" выше), не на уровне инфраструктуры.

## Операционные требования (путь Solana)

- **У Solana нет публичного pending-мемпула** для сторонних searcher'ов —
  приватный shred-stream Jito требует отдельного одобрения. Watcher наблюдает
  не "ожидающую" транзакцию, а изменение резервов пула сразу после того, как
  своп уже подтверждён — гонка идёт за следующий слот, не за тот же блок.
- **Watchlist по конкретным кошелькам для арбитражного пути** (`main.py`) не
  реализован — `accountSubscribe` на vault-аккаунт не даёт отправителя. Для
  копитрейдинга (`copytrade.py`) watchlist есть — через отдельный
  `wallet_watcher.py` (см. секцию "Копитрейдинг" ниже).
- Ноги свопа строит Jupiter (`jupiter_python_sdk`), а не собственная кодировка
  инструкций Raydium — там ~18 аккаунтов и PDA-деривации, которые нельзя
  проверить без devnet. Таргетинг на пул — на уровне DEX через `exclude_dexes`,
  не гарантированно на уровне конкретного `pool_id`.
- `reference_pools`/`pools` должны указывать реальные адреса base/quote
  vault-аккаунтов и label DEX, который понимает Jupiter (`"Raydium"`,
  `"Orca"` и т.п.).
- Требует, чтобы у кошелька `SOLANA_PRIVATE_KEY` уже были ассоциированные
  token-аккаунты (ATA) под задействованные токены — Jupiter их не создаёт на лету.
- Bundle без tip-транзакции Jito block engine не рассматривает вообще — это
  встроенный обязательный аналог builder-payment, не опциональная настройка.
  Tip-аккаунт запрашивается динамически через `getTipAccounts`, не хардкодится.

## Quant-hardening (обе сети)

- **Token allowlist**: `token_allowlist` — не автодетектор honeypot'ов
  (ненадёжен без анализа байткода), а явная, проверяемая граница того, что и
  так подразумевалось: бот торгует только заранее сконфигурированными
  токенами. Пустой allowlist = проверка выключена (для дева/тестов); в
  проде указывайте явно.
- **Token denylist**: `token_denylist` — курируемый вручную список известных
  fee-on-transfer/rebasing токенов (та же причина, что и с allowlist —
  автоматический анализ байткода ненадёжен, поэтому списка по умолчанию
  нет). Такие токены ломают допущение `apply_swap()`/`get_amount_out()` о
  сохранении суммы при переводе. На арбитражных путях проверяется при
  старте (пулы известны заранее); на копитрейдинге — по каждому свопу в
  рантайме (токены заранее не известны).
- **Адаптивный tip**: `PROFIT_SHARE_BPS` — это стартовое значение, дальше им
  управляет `AdaptiveTipController` (AIMD) — не попал бандл в блок, ставка
  растёт; попал — немного снижается, оставляя больше маржи. Не ML/bandit,
  просто тот же принцип, что управление перегрузкой в TCP.
- **Pre-flight симуляция бандла** (ETH): `FlashbotsBundleSender` всегда
  симулирует бандл через Flashbots (`w3.flashbots.simulate`) прямо перед
  отправкой — если симуляция вернула ошибку (например, реверт из-за
  устаревших резервов), бандл вообще не отправляется. Не наша офлайн-математика
  ещё раз, а реальный прогон на актуальном состоянии сети.
- **Мульти-relay отправка** (ETH): `ETH_RELAY_URLS` — один и тот же
  подписанный бандл уходит параллельно во все настроенные relay (у каждого
  свой набор builder'ов, поэтому это реально увеличивает шанс попасть в
  блок). Дефолт — только Flashbots.
- **Прямая отправка билдерам** (не только через relay-агрегатор): рынок
  билдинга блоков фрагментирован — beaverbuild, rsync-builder, Titan,
  builder0x69 и другие каждый строят СВОЮ долю блоков; бандл, отправленный
  только в Flashbots relay, физически не может попасть в блок другого
  билдера. `eth_sendBundle` — стандартный JSON-RPC метод, одинаковый у
  большинства прямых builder-эндпоинтов (подтверждено против исходников
  `flashbots`-пакета: `sendBundle` = `Method(FlashbotsRPC.eth_sendBundle, ...)`,
  ничего relay-специфичного) — значит `ETH_RELAY_URLS` уже умеет их принимать
  БЕЗ изменений в коде, просто добавьте URL в список. `FlashbotsBundleSender`
  симулирует ОДИН раз через первый клиент (обычно Flashbots — единственный
  relay в этом списке с гарантированной поддержкой `eth_callBundle`), а
  реальную отправку делает параллельно во ВСЕ настроенные клиенты — правка
  send-пути не требуется. Большинство прямых builder RPC не требуют
  авторизации (пустая позиция в `ETH_RELAY_API_KEYS`). Актуальный список
  зарегистрированных builder-эндпоинтов:
  [flashbots/dowg builder-registrations.json](https://github.com/flashbots/dowg/blob/main/builder-registrations.json)
  — **проверьте URL сами** перед использованием (список меняется, я не смог
  независимо подтвердить живость всех адресов из своей песочницы с
  ограниченным DNS).
- **Авторизация non-Flashbots relay** (bloXroute, Eden и т.п.):
  `ETH_RELAY_API_KEYS` — ПОЗИЦИОННО к `ETH_RELAY_URLS` (пустая позиция =
  для этого конкретного relay без авторизации, Flashbots и так работает
  без неё). Отправляется как заголовок `Authorization: <ключ>` —
  `flashbots`-пакет сам добавляет только `X-Flashbots-Signature`
  (`chains/eth/sender.py:_AuthedFlashbotProvider` домешивает второй
  заголовок). Общий случай bearer-токена — relay с другой схемой
  авторизации (не заголовок `Authorization`) потребуют доработки
  `sender.py`.
- **Гонка RPC-провайдеров** (обе сети, `wakefinder/common/race.py`):
  `ETH_RPC_WS_URLS` / `SOLANA_RPC_WS_URLS` — дополнительные WS-провайдеры
  сверх основного `*_RPC_WS_URL`, каждый со своим watcher'ом (`UniswapV2Watcher`
  на ETH, `RaydiumVaultWatcher`/`WalletSwapWatcher` на Solana) и своим
  `with_reconnect`. Все смотрят один и тот же источник независимо (разное
  пиринг-соединение — разная задержка), первый, увидевший конкретное событие
  (pending-tx на ETH, изменение резервов/лог кошелька на Solana), выигрывает
  гонку, дубликаты от остальных провайдеров молча отбрасываются (на ETH — по
  `tx_hash`). Основной `*_RPC_WS_URL` остаётся единственным источником для
  симуляции и отправки — гонка только про скорость ОБНАРУЖЕНИЯ, не про
  дублирование исполнения. Пусто по умолчанию = гонка выключена, поведение как
  с одним провайдером (без накладных расходов на очередь/дедуп). Wired во все
  4 энтрипоинта (`eth/main.py`, `eth/copytrade.py`, `solana/main.py`,
  `solana/copytrade.py`).
- **Сверка исполнения** (`wakefinder/common/reconciliation.py`, обе сети):
  после подтверждённого включения бот перечитывает баланс `token_in` и
  логирует `realized_profit` рядом с `expected_profit` в `trade_log.jsonl` —
  постфактум-аудит точности симуляции, не влияет на решение о входе (число
  доступно только после того, как сделка уже произошла).
- **Конвертация газа/кэпа для не-WETH token_in** (ETH): газ и
  `MAX_CAPITAL_PER_BUNDLE_ETH` считаются в реальных ETH wei, но арбитражная
  математика сравнивает их с прибылью в единицах `token_in`. `TwoPoolArbSimulator`
  конвертирует через `getAmountsOut(WETH → token_in)` на целевом роутере,
  если `token_in` не сам WETH (`ETH_WETH_ADDRESS`); нет прямой пары — сделка
  пропускается с явной причиной, не тихим нулём. На Solana — тот же принцип:
  конвертация через Jupiter-квоту `wSOL → token_in` (`SOLANA_WSOL_ADDRESS`),
  быстрый путь без запроса сохранён для `token_in == wSOL`.
- **Автостоп по сериям неудач**: `MAX_CONSECUTIVE_FAILURES` (по умолчанию 5) —
  после стольких подряд непопавших в блок бандлов бот сам ставит kill switch.
  Не защита от прямой потери денег (неотправленный/непопавший бандл ничего не
  стоит), а сигнал "что-то системно не так", который нельзя оставлять
  человеку заметить самому.
- **Лог сделок**: `TRADE_LOG_FILE` (по умолчанию `trades.jsonl`) — append-only
  JSONL с каждой попыткой (симулированная прибыль, попал ли в блок, tx-ссылки).
  Не полноценный PnL-дашборд — тот потребовал бы снимков баланса до/после
  каждой сделки, это отдельная задача; здесь только сырые данные для анализа.
- **Приоритизация возможностей в арбитраже — сознательно не реализована.**
  MEV-возможности живут доли секунды; буферизация нескольких для сравнения
  сделала бы котировки устаревшими к моменту выбора. (Для копитрейдинга,
  где позиция держится минутами/часами, буферизация УМЕСТНА — см. консенсус ниже.)

## Копитрейдинг (`wakefinder/chains/{eth,solana}/copytrade.py`)

Принципиально другая стратегия, чем backrun-арбитраж (`main.py`/`simulator.py`):
не арбитражим ценовой перекос от сделки кита, а **зеркалим её направление** —
покупаем то же, что купил watched-кошелёк, держим позицию, продаём позже.
**Другой профиль риска**: арбитраж никогда не держит инвентарь дольше одного
атомарного бандла (гарантированная на момент исполнения прибыль или ничего);
копитрейдинг реально держит открытую направленную позицию между входом и
выходом — это не гарантированно прибыльная сделка, это ставка.

- **Размер позиции — доля НАШЕГО баланса** (`COPYTRADE_SIZE_PCT`, по
  умолчанию 2%), не сумма кита. У кита может быть бюджет в миллионы, у нас —
  сколько есть; бот копирует направление ставки, не её абсолютный размер.
  Пересчитывается заново перед каждым входом по текущему балансу.
- **Win-rate множитель размера** (`wakefinder/common/position_sizing.py`) —
  не полноценный Kelly criterion (для него нужны парные P&L по каждой сделке,
  у нас только агрегированные суммы, см. docstring `wallet_stats.py`), а
  честный более простой прокси: кошелёк с историческим win rate выше 50%
  получает БОЛЬШЕ размера на новый вход (до `COPYTRADE_SIZING_MAX_MULTIPLIER`,
  по умолчанию 1.5x), с win rate ниже — МЕНЬШЕ (до `_MIN_MULTIPLIER`, 0.25x).
  Не корректирует размер, пока по кошельку не накопилось
  `COPYTRADE_SIZING_MIN_TRADES` (по умолчанию 5) подтверждённых выходов —
  на малой выборке win rate статистически бессмысленен.
- **Вход требует консенсуса**: `COPYTRADE_MIN_CONSENSUS_WALLETS` (по
  умолчанию 2) разных watched-кошельков должны купить один и тот же токен в
  течение `COPYTRADE_CONSENSUS_WINDOW_SECONDS` (по умолчанию 120с) — один кит
  может ошибаться, несколько независимых, сходящихся почти одновременно —
  сильнее сигнал. Логика — `wakefinder/common/consensus.py`. Это САМЫЙ
  большой рычаг скорости в пайплайне — см. "Мемкоин-профиль" выше про то,
  как его тюнить под скорость.
- **Выход по двум независимым триггерам**: зеркальный (watched-кошелёк
  продаёт токен, который мы держим) ИЛИ стоп-лосс (`COPYTRADE_STOP_LOSS_PCT`,
  по умолчанию 20%, проверка каждые `COPYTRADE_STOP_LOSS_CHECK_INTERVAL_SECONDS`
  = 60с фоновой задачей) — защита на случай, если все киты держат "до нуля"
  или мы упустили их выход.
- **Позиции — плоский JSON-файл** (`COPYTRADE_POSITIONS_FILE` /
  `SOLANA_COPYTRADE_POSITIONS_FILE`), переживает рестарт — краш с открытой
  позицией не значит молча забытый риск.
- **ETH**: следует за китом в ЛЮБОЙ токен, не только предсконфигурированный —
  адрес пула при промахе по `pool_registry` выводится через `getPair()`
  фабрики Uniswap V2 (`ETH_FACTORY_ADDRESS`), включается только для
  watchlist-триггеров, не меняет поведение арбитражного пути.
- **Solana**: свой watcher (`wallet_watcher.py`) — DEX-агностичный, читает
  `preTokenBalances`/`postTokenBalances` подписчика из транзакции (через
  `logsSubscribe(mentions=[wallet])` на `commitment=Processed` — самый быстрый
  публичный уровень; сама транзакция выбирается на `commitment=Confirmed` с
  короткими повторами, `processed` для `getTransaction` в основном не
  поддерживается публичными RPC), а не декодирует инструкции конкретного DEX.
  Работает одинаково для Raydium/Orca/Jupiter/чего угодно ещё, которым мог
  торговать отслеживаемый кошелёк.
- **ETH-скорость входа**: собственные сделки копитрейдинга (вход и выход) идут
  в ПУБЛИЧНЫЙ мемпул (`send_raw_transaction`), не через Flashbots — сознательный
  выбор в пользу скорости, в обмен на риск быть засэндвиченным другими
  MEV-ботами — та же атака, которую применяет арбитражная часть этого
  проекта против чужих сделок.
- **Кэп суммарной экспозиции**: `COPYTRADE_MAX_TOTAL_EXPOSURE_PCT` (по
  умолчанию 20%) — ограничивает не одну сделку, а сумму entry_amount_in по
  ВСЕМ открытым позициям сразу; без этого несколько последовательных входов
  по `COPYTRADE_SIZE_PCT` каждый могли бы незаметно съесть большую часть баланса.
- **Требует ОТДЕЛЬНОГО процесса** от `main.py` (арбитраж) — если использовать
  тот же кошелёк одновременно с обеими стратегиями, они независимо считают
  nonce/отправляют транзакции и будут конфликтовать. Разделяйте кошельки или
  не запускайте одновременно.

## Memecoin-снайпинг (`wakefinder/chains/eth/snipe.py`)

Третья, принципиально отдельная стратегия — не арбитраж (нет ценового
перекоса между пулами) и не копитрейдинг (нет кита, за которым следить).
Реагирует на сам факт появления новой пары на Uniswap V2 Factory
(`PairCreated`), проходит дешёвый safety-фильтр и входит по моментуму;
выходит по trailing-stop, а не по внешнему сигналу.

- **Watcher, дефолтный режим** (`chains/eth/pair_watcher.py`): подписка на
  `PairCreated` Factory — уже СМАЙНЕННОЕ событие, вход после этого идёт через
  публичный мемпул. Простой и надёжный путь, но не конкурентен по скорости с
  другими снайпер-ботами, которые реагируют раньше.
- **Backrun-снайпинг** (`SNIPE_BACKRUN_MODE=true`,
  `chains/eth/liquidity_watcher.py:LiquidityAddWatcher`): реагирует на
  PENDING `addLiquidityETH` создателя пары (Uniswap V2 Router сам вызывает
  `factory.createPair()` внутри, если пары ещё нет — это и есть момент
  запуска токена на практике) и покупает ОДНИМ Flashbots-бандлом
  `[victim_raw, buy_raw]` на `target_block = block_number + 1` — тот же
  принцип backrun'а, что уже работает в `main.py` для арбитража, применённый
  к снайпингу. Реально конкурентно по скорости с другими ботами, в отличие от
  дефолтного режима. Котировка на вход считается через
  `common/amm.py:get_amount_out` по `amountTokenDesired`/`msg.value` из
  calldata victim-транзакции (НАМЕРЕНИЕ создателя, не гарантированный факт —
  `router.getAmountsOut()` не сработал бы, пары ещё нет на цепи), не через
  реальный запрос к пулу. Round-trip honeypot-проверка (уровень 2 ниже) в
  этом режиме тоже адаптирована — `check_backrun_sellable` добавляет
  `victim_raw` первой ногой симуляции. Выключено по умолчанию — новее и
  меньше проверено в бою, чем остальные пути проекта; включайте осознанно
  (пример профиля — `configs/eth-snipe-backrun.toml`).
- **Safety-фильтр, уровень 1** (`chains/eth/snipe_filter.py:check_new_pool`):
  дешёвые проверки без единой подписанной транзакции — минимальная
  ликвидность WETH-стороны (`SNIPE_MIN_LIQUIDITY_WETH`) и то, что
  AMM-математика вообще считается в обе стороны (`getAmountsOut` buy+sell
  quote). НЕ ловит honeypot, где математика в порядке, а сам `transfer`/
  `transferFrom` токена блокирует продажу.
- **Safety-фильтр, уровень 2** (`check_round_trip_sellable`,
  `SNIPE_ROUND_TRIP_CHECK`, по умолчанию включён): РЕАЛЬНАЯ round-trip
  симуляция — подписанные `[buy, approve, sell]` с последовательными nonce,
  прогнанные через `FlashbotsBundleSender.simulate()` (ничего не
  отправляется, только считается) против одного снапшота состояния — та же
  механика, на которой держится backrun-арбитраж в `main.py`. Ловит
  transfer-блокирующие honeypot'ы, которые уровень 1 не видит. Всё ещё НЕ
  гарантия: time-locked honeypot (продажа блокируется только через N
  блоков) не поймает — проверяет "можно продать ПРЯМО СЕЙЧАС", не "всегда".
  Байткод-анализ (третий, более глубокий уровень) сознательно не
  реализован — ненадёжен даже как эвристика, та же логика, что у
  allowlist/denylist (см. "Quant-hardening"): ненадёжная автоматическая
  проверка хуже честного явного ограничения.
- **Стоит дополнительной задержки перед входом**: round-trip симуляция —
  ещё один сетевой RPC-вызов между обнаружением пула и реальным входом.
  Выключите `SNIPE_ROUND_TRIP_CHECK`, если скорость важнее.
- **Вход**: момент, фиксированный `SNIPE_SIZE_PCT` от баланса — не
  win-rate/Kelly-подобный размер, как в копитрейдинге, потому что у нового
  токена физически нет истории для расчёта.
- **Выход** (`common/trailing_stop.py`): trailing-stop от локального пика
  после входа (`SNIPE_TRAILING_STOP_PCT`), не фиксированный стоп-лосс от
  цены входа — держит часть движения вверх при памп-и-дампе вместо отдачи
  всей прибыли обратно рынку. Фоновая задача проверяет каждые
  `SNIPE_TRAILING_STOP_CHECK_INTERVAL_SECONDS`.
- **Одноразовый `approve`**: токен неизвестен заранее (в отличие от
  предварительно заапрувленных роутеров, см. "Операционные требования"), так
  что approve на router отправляется по факту первого успешного входа, перед
  тем как позиция вообще может понадобиться продать.
- **Скорость входа**: в дефолтном режиме вход и выход идут в ПУБЛИЧНЫЙ мемпул
  напрямую, не через Flashbots — тот же компромисс скорости против
  sandwich-риска, что у копитрейдинга. В `SNIPE_BACKRUN_MODE` вход идёт через
  Flashbots (см. выше), выход всё равно остаётся в публичном мемпуле — на
  момент выхода позиция уже открыта, той же гонки за same-block входом нет.
- **РИСК**: подавляющее большинство новых пар — rug/dead в первые минуты.
  Держите `SNIPE_SIZE_PCT` маленьким, используйте `canary_start_fraction` на
  новом профиле (см. "Поэтапный ввод капитала"), отдельный кошелёк от других
  3 стратегий (nonce-конфликт при общем `ETH_PRIVATE_KEY`, то же
  ограничение, что у всех ETH-путей). Пример профиля — `configs/eth-snipe.toml`.

## Снайпинг на Solana (`wakefinder/chains/solana/snipe.py`)

Тот же принцип, что ETH-снайпинг выше, но детекция устроена ПРИНЦИПИАЛЬНО
иначе — намеренно, не случайно.

- **Почему не как на ETH**: у Uniswap V2 есть один стабильный, ABI-описанный
  `PairCreated` от одной фабрики — можно с уверенностью распарсить, не имея
  доступа к живой сети. На Solana аналога "фабрики создания пула" с одним
  стабильным форматом нет — у каждого AMM (Raydium AMM V4, Raydium CLMM,
  Orca Whirlpool, ...) свой program ID и свой набор accounts под инструкцию
  создания пула, а в этом проекте нет живого Solana-валидатора для
  fork-теста такого парсинга (в отличие от anvil для ETH, см.
  "Fork-тесты") — риск тихо ошибиться в layout слишком велик для реальных
  денег.
- **Watcher** (`chains/solana/mint_watcher.py`): вместо этого — сигнал
  создания НОВОГО МИНТА (`TOKEN_PROGRAM_ID`, `InitializeMint`/
  `InitializeMint2` — фундаментальная, стабильная, используемая буквально
  всеми часть SPL Token Program). Большинство новых минтов НИКОГДА не
  получают пул вообще — это ожидаемо, не проблема watcher'а.
- **Safety-фильтр** (`chains/solana/snipe_filter.py:check_mint_tradeable`):
  единственная реальная проверка торгуемости — котировка через Jupiter в
  ОБЕ стороны (`SOLANA_SNIPE_MIN_LIQUIDITY_SOL`). Если Jupiter — который
  агрегирует все DEX и возвращает маршрут, только если он реально
  существует, — не может посчитать маршрут, ликвидности нет. Это медленнее
  ETH-варианта (Jupiter индексирует новый пул не мгновенно), но не
  полагается на непроверенное здесь знание о чужом account-layout.
- **Вход/выход**: полностью через Jupiter + Jito bundle с tip — тот же
  проверенный путь, что копитрейдинг (`copytrade.py:_swap_via_jupiter_and_send`,
  переиспользуется напрямую), не собственное кодирование инструкций DEX.
  Trailing-stop — та же логика (`common/trailing_stop.py`), что у ETH.
- **РИСК**: тот же, что у ETH-снайпинга — подавляющее большинство новых
  минтов rug/dead. Держите `SNIPE_SIZE_PCT` маленьким, canary на новом
  профиле, отдельный кошелёк от `main.py`/`copytrade.py`. Пример профиля —
  `configs/solana-snipe.toml`.

## Наблюдаемость

- **Трекинг результативности кошельков** (`wakefinder/common/wallet_stats.py`):
  агрегирует `trade_log.jsonl` по полю `wallet` (записи `copytrade_entry`/
  `copytrade_exit`) — приблизительный net PnL и win rate на кошелёк, чтобы видеть,
  какие watched-кошельки из вашего списка реально прибыльны. Оценка на
  котируемых, не аудированных постфактум суммах (см. docstring модуля).
- **История PnL** (`wakefinder/common/pnl_ledger.py`, `PNL_LEDGER_FILE`): в
  отличие от `trade_log.jsonl`, где вход и выход копитрейдинга/снайпинга —
  две независимые записи попыток, здесь одна запись = одна РЕАЛЬНО ЗАКРЫТАЯ
  сделка (`entry`/`exit` уже смэтчены, посчитан `realized_pnl`) — для
  арбитража это та же цифра, что и `realized_profit` в trade_log (сделка
  атомарна). Пишется только при `included=True` — без попадания в блок нет
  честных чисел для записи. Видна на веб-дашборде (таблица "История закрытых
  сделок") и в `GET /api/state` (`pnl_history`), самые свежие сделки первыми.
- **Latency: детекция → отправка** (`PendingSwap.detected_at`/`NewPool.detected_at`/
  `PendingLiquidityAdd.detected_at`/`NewMint.detected_at` в `common/interfaces.py`):
  каждый watcher проставляет метку времени в момент, когда РЕШИЛ, что событие
  важно — не момент появления в мемпуле ноды (этого бот не видит), а начало
  СОБСТВЕННОГО пайплайна реакции. На каждой ENTRY-попытке (арбитраж,
  копитрейд-вход, снайп-вход — обычным и backrun-путём) считается
  `latency_ms = (время перед отправкой − detected_at) × 1000` и пишется в
  `trade_log.jsonl`. `common/metrics.py:compute_chain_metrics` агрегирует
  `avg_latency_ms`/`median_latency_ms` на сеть — видно в таблице "Метрики" на
  дашборде и в `GET /metrics` (`wakefinder_avg_latency_ms`/
  `wakefinder_median_latency_ms`, с лейблом `chain`). Это НЕ полная задержка
  от появления транзакции в сети — честная нижняя граница именно НАШЕГО
  времени реакции, единственное, что код может измерить и на что может
  повлиять.
- **CLI-дашборд**: `python -m wakefinder.dashboard` — печатает открытые позиции
  (ETH/Solana) и статистику по кошелькам в терминал. Переиспользует
  `wallet_stats.py`, никакого веб-сервера.
- **Веб-дашборд** (`wakefinder/web.py`, опциональная зависимость): FastAPI-
  сервер с ЖИВЫМИ данными, не только файловыми — `wakefinder/live_state.py`
  подключается к RPC напрямую (баланс кошелька ETH/SOL, текущая оценка
  каждой открытой позиции через `getAmountsOut`/Jupiter `quote()` прямо
  сейчас, не только `entry_amount_in` из момента входа) плюс всё, что было
  раньше (`wallet_stats.py`/`price_feed.py`/`killswitch.py`/`heartbeat.py`,
  метрики `wakefinder/common/metrics.py`). Страница — статичный HTML-каркас,
  все данные приходят через `GET /api/state` (тот же JSON, который бы
  использовал Telegram MiniApp или другой клиент) и опрашиваются JS каждые
  3с, перерисовывая DOM без перезагрузки — не WebSocket, поллинга достаточно
  для одного локального пользователя, без накладных расходов на broadcast.
  Ошибка RPC (ETH или Solana недоступен) не валит весь дашборд — конкретная
  секция показывает `eth_error`/`solana_error`, остальное (kill switch,
  метрики, heartbeat) продолжает отображаться. Установка и запуск:
  ```bash
  pip install -e ".[web]"
  uvicorn wakefinder.web:app --reload
  ```
  Открыть `http://127.0.0.1:8000`. Торговые процессы не знают о существовании
  этого модуля и не зависят от него — можно не устанавливать `[web]` вовсе.
- **Desktop-приложение**: `wakefinder/launcher.py` — один процесс поднимает
  сервер и сам открывает браузер (`python -m wakefinder.launcher` или
  установленная команда `wakefinder-dashboard`), вместо ручного запуска
  uvicorn и перехода по адресу. Чтобы получить двойной клик — `.exe`/`.app`
  вместо команды в терминале — соберите через
  [PyInstaller](https://pyinstaller.org/):
  ```bash
  pip install -e ".[web]" pyinstaller
  pyinstaller --onefile --name wakefinder-dashboard --collect-all uvicorn --collect-all fastapi wakefinder/launcher.py
  ```
  Бинарник появится в `dist/`. **Важно**: PyInstaller собирает бинарник ПОД
  ТУ ОС, на которой запущен сам процесс сборки — Windows `.exe` нужно
  собирать на Windows, macOS `.app`/бинарник на macOS и т.д., кросс-сборки
  нет. `.env` (или переменные окружения) всё ещё нужны рядом с бинарником —
  секреты не встраиваются в exe.
- **Аутентификация дашборда**: `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD` —
  HTTP Basic на `/` (сравнение через `secrets.compare_digest`, `/health`
  остаётся открытым для liveness-проб). Обе переменные опциональны, но
  обязаны быть заданы ВМЕСТЕ — если не заданы, дашборд отдаётся без
  аутентификации и при старте пишет громкий warning в лог. Задавайте их,
  если планируете открыть порт дальше localhost.
- **USD-оценка** (`wakefinder/common/price_feed.py`): дашборд подтягивает
  курс ETH/SOL с публичного CoinGecko endpoint (без API-ключа) и показывает
  `net_pnl~` ещё и в `$` рядом с нативными единицами — `--no-usd`, чтобы
  пропустить сетевой запрос (офлайн/приватность). Только для отображения:
  торговая логика (drawdown, кэпы) остаётся в нативных единицах — см.
  docstring `drawdown.py`, почему конвертация туда сознательно не добавлена.
- **Telegram-алерты** (`wakefinder/common/alerts.py`): `TELEGRAM_BOT_TOKEN` /
  `TELEGRAM_CHAT_ID` — уведомления на kill switch (ручной и авто по сериям
  неудач) и стоп-лосс копитрейдинга. Пустые значения = алерты выключены.
- **Сканер кандидатов в watchlist** (`wakefinder/wallet_scanner.py`) — НЕ
  рейтинг прибыльности (для этого нужна была бы полная реконструкция истории
  каждого кандидата, по сложности не уступающая бэктестингу под каждого
  отдельно), а дешёвый первый фильтр — см. "Быстрый старт" шаг 4.

## Telegram MiniApp (`/telegram` в web.py, `wakefinder/telegram_auth.py`)

Удалённое управление ботом через Telegram — тот же дашборд (баланс,
позиции, kill switch, живой конфиг), только внутри Telegram-клиента, для
случая, когда бот развёрнут на удалённом сервере, а не запущен локально.

- **Аутентификация**: Telegram Web Apps подписывают `initData` через
  HMAC-SHA256 с ключом, производным от `TELEGRAM_BOT_TOKEN`
  (`wakefinder/telegram_auth.py:verify_init_data`, по официальному
  [алгоритму Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-web-app)) —
  подделать подпись без токена бота невозможно. Это доказывает "запрос от
  Telegram для этого user_id", НЕ "этому user_id можно управлять ботом" —
  вторая, отдельная проверка: `TELEGRAM_ALLOWED_USER_ID` (числовой Telegram
  user_id владельца). Пусто по умолчанию = все MiniApp-эндпоинты отклоняют
  вообще всё (безопасный дефолт, не "открыто всем с Telegram-аккаунтом").
- **Настройка бота** (у @BotFather, вручную — API для этого не
  автоматизировано здесь): `/newapp` на существующего бота, указать URL
  `https://ваш-домен/telegram`. **Обязательно HTTPS и публичная
  доступность** — Telegram не откроет `http://` или `localhost` внутри
  клиента. Для локального теста — туннель (Cloudflare Tunnel/ngrok), для
  прод-развёртывания — обратный прокси (Caddy/nginx) с TLS-сертификатом
  перед `uvicorn`. Ни то, ни другое не входит в этот проект — это
  инфраструктура хостинга, не код бота.
- **Функции**: те же данные, что desktop-дашборд (`GET /api/telegram/state`),
  включение/выключение kill switch (`POST /api/telegram/killswitch`), правка
  живого конфига (`GET`/`POST /api/telegram/config`) — компактный
  мобильный layout, не копия десктопной страницы.
- **Отдельные эндпоинты от `/api/state`/`/api/config`**: у Basic-auth
  дашборда и Telegram MiniApp разные механизмы проверки личности, поэтому
  разные dependency-функции (`_check_auth` / `_check_telegram_auth`) и
  разные пути — не смешиваются, каждый эндпоинт понимает ровно один способ
  аутентификации.

## Живой конфиг (`wakefinder/live_config.py`)

Дашборд и Telegram MiniApp правят `watched_wallets`/`token_allowlist`/
`token_denylist`/риск-параметры БЕЗ перезапуска бота — через JSON-редактор
на обеих страницах (`/api/config` и `/api/telegram/config`).

- **Механизм**: файл на диске (`LIVE_CONFIG_FILE`, по умолчанию
  `live_config.json`), который дашборд/MiniApp пишут, а торговый процесс
  перечитывает каждые `LIVE_CONFIG_CHECK_INTERVAL_SECONDS` (по умолчанию
  10с) — тот же принцип, что kill switch: дашборд и торговые процессы —
  РАЗНЫЕ ОС-процессы без общей памяти, файл на диске — единственный
  работающий канал между ними. "Динамически" значит "на следующем опросе",
  не мгновенно в тот же тик.
- **Первый запуск**: при старте профиль/CLI-параметры (`watched_wallets` и
  т.п. из TOML) один раз переносятся (`seed_if_missing`) в `live_config.json`,
  если файла ещё нет — дальше файл единственный источник правды, профиль
  больше не участвует, редактируйте через дашборд/MiniApp.
- **Область действия (честно ограничено)**: `watched_wallets` живой и на ETH
  (копитрейдинг и factory-фолбэк арбитража), и на Solana копитрейдинге —
  `WalletSwapWatcher` сам периодически (каждые
  `SUBSCRIPTION_SYNC_INTERVAL_SECONDS`, по умолчанию 5с, чаще при активном
  трафике — сверка идёт и после каждого полученного батча уведомлений)
  сверяет `self.watched_wallets` и до/отписывает `logs_subscribe` без
  реконнекта WebSocket-соединения.
  `token_allowlist`/`token_denylist` живые везде, где есть per-swap проверка
  (копитрейдинг, снайпинг) — НЕ для арбитража, где они проверяются один раз
  при старте против фиксированного набора пулов. Риск-параметры (тот же
  список ключей, что `[risk]` в TOML-профилях, `cli.py:_RISK_ENV_MAP`)
  живые везде. **Пулы арбитража тоже живые**: `reference_pools` (обе сети) и
  `pool_registry` (только ETH) редактируются через тот же JSON-редактор.
  ETH-симулятор/watcher читают свои dict'ы свежими на каждый вызов — правка
  сводится к мутации in place, без пересборки. Solana `RaydiumVaultWatcher`
  подписывается на vault-аккаунты и поэтому сам периодически (тот же
  `SUBSCRIPTION_SYNC_INTERVAL_SECONDS`, что у `WalletSwapWatcher`) до/
  отписывает `accountSubscribe` под изменившийся `solana_pools` — тоже без
  реконнекта.
- **Несколько профилей одновременно**: `live_config_file` по умолчанию ОБЩИЙ
  на все процессы (то же допущение, что `kill_switch_file`) — задайте
  разные `live_config_file` в разных TOML-профилях (`configs/*.toml`), если
  запускаете несколько стратегий одновременно, иначе они будут читать/писать
  один и тот же watched_wallets/denylist друг у друга.
- **Атомарная запись**: `save_live_config` пишет во временный файл и делает
  `os.replace` — единственное место в проекте, где один процесс регулярно
  ПИШЕТ файл, который другой процесс регулярно ЧИТАЕТ с сопоставимой
  частотой, поэтому здесь (в отличие от файлов позиций) стоит защититься от
  частично записанного JSON.

## Живые графики позиций (`wakefinder/common/price_history.py`)

Клик по токену в любой таблице открытых позиций на desktop-дашборде рисует
линейный график через [lightweight-charts](https://github.com/tradingview/lightweight-charts)
(та же команда, что делает TradingView, но эта библиотека — открытый
отдельный проект, не сам терминал TradingView).

- **Откуда данные**: НЕ архивная реконструкция цены пула через прошлые
  блоки — это дорого (много RPC-вызовов) и не все публичные RPC вообще
  поддерживают запросы к произвольному прошлому блоку, особенно для только
  что созданных мемкоин-пулов. Вместо этого — побочный эффект уже
  выполняемого запроса: каждый раз, когда `/api/state` успешно получает
  `current_value` открытой позиции (`getAmountsOut`/Jupiter `quote()`, тот
  же запрос, что и для отображения в таблице), точка попутно пишется в
  `PRICE_HISTORY_FILE` (JSONL, `{ts, token, value}`).
- **Честное следствие**: история копится только за то время, что дашборд
  был ОТКРЫТ И ОПРАШИВАЛ `/api/state` — если дашборд не запущен несколько
  часов, за эти часы в графике будет дыра. Не баг, а прямое следствие того,
  что это не архивные данные.
- **API**: `GET /api/price_history?token=0x...` (Basic auth, тот же
  механизм, что `/api/state`) — только на desktop-дашборде; Telegram
  MiniApp его не показывает (мобильный экран, ниже ценность/усилие для
  графика, чем для баланса/kill switch/live-конфига).
- **Внешняя зависимость**: `lightweight-charts` подключается с CDN
  (`unpkg.com`) прямо в браузере — не добавляет зависимость в
  `pyproject.toml`, тот же принцип, что `telegram-web-app.js` в MiniApp.

## Prometheus/Grafana (`GET /metrics`)

Дашборд отдаёт метрики в стандартном Prometheus text exposition формате —
переиспользует то же `gather_state()`, что и `/api/state` (не отдельный
источник правды), просто другой рендер того же снимка состояния.

- **Что публикуется**: `wakefinder_kill_switch_engaged`, `wakefinder_eth_balance`/
  `wakefinder_sol_balance`, `wakefinder_heartbeat_age_seconds`/`_stale` (per
  `process`), `wakefinder_trade_attempts_total`/`_included_total`/`_fill_rate`/
  `_avg_expected_profit`/`_avg_realized_profit`/`_simulation_accuracy` (per
  `chain`). `None`-значения (например, RPC недоступен) просто не публикуются —
  Prometheus не поддерживает null, тихое отсутствие сэмпла лучше, чем `0`,
  который выглядел бы как реальный ноль.
- **Настройка Prometheus**: обычный `scrape_config` с `metrics_path: /metrics`
  на адрес дашборда. Если заданы `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD` —
  добавьте `basic_auth: {username, password}` в тот же job (тот же
  `_check_auth`, что и у `/api/state`, `/metrics` не исключение).
- **Grafana**: подключается к Prometheus как к datasource, дашборд строится
  в Grafana поверх метрик выше — сам проект дашборды Grafana не поставляет.
- **Без новой зависимости**: формат собирается вручную (`wakefinder/live_state.py:render_prometheus`),
  не через пакет `prometheus_client` — для горстки gauge-метрик собственный
  рендер проще, чем тянуть библиотеку. `# HELP`/`# TYPE` — ровно один раз на
  имя метрики перед всеми её сэмплами, как того требует exposition format
  (несколько таких блоков на одно имя `promtool`/Prometheus отклонят).

### Fork-тесты

`tests/test_fork_integration.py` — прогоняет реальный `TwoPoolArbSimulator`
против настоящего форкнутого состояния mainnet (через
[anvil](https://book.getfoundry.sh/anvil/), не заглушки) — ловит расхождение
между нашими ABI-фрагментами (`chains/eth/abi.py`) и реальным задеплоенным
байткодом Uniswap V2/Sushiswap, чего моки в остальных тестах структурно не
могут поймать.

Установка (один раз): `curl -L https://foundry.paradigm.xyz | bash && foundryup`
(на macOS может понадобиться `brew install libusb`). Без `anvil` в PATH эти
конкретные тесты просто помечаются `skipped`, весь остальной `pytest tests/`
не затронут. В CI ставится автоматически через `foundry-rs/foundry-toolchain`.
